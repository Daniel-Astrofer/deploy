## Admission and restore boundary

The TLS admission server lives in `kerosene-csi-qualification`, outside the
isolated restore namespaces. It has no Kubernetes API token or RBAC. Its
immutable ConfigMap holds API-defaulted, exact reviewed Pod specs derived from
the production `PROBE` and `pod_spec` AST nodes. An admission webhook with
`failurePolicy: Fail` selects exact namespace names using CEL, not removable
labels. It validates after mutating admission and rejects extra/changed spec
fields rather than accepting a subset. Scheduler node binding and the PV
controller's volume binding are narrowly allowed; status subresources are
excluded. The namespace controller may create only an inert default service
account. Exact restore/check account credentials are forbidden.

Actual CREATE denials cover writable data/root mounts, writable/additional
volumes, token automount, projected credentials, Secret environment references,
pull credentials, sidecars, init containers, daemon/unreviewed commands,
mutable images, host networking, privilege, controllers, Services, Secrets and
RBAC. Denials must contain the admission server's specific boundary marker;
syntax errors or unrelated Pod Security rejections do not count. A dry-run
unreviewed command confirms the webhook is active before live negative requests.
Already captured denials are not repeated when resuming a partial run.

The approval declaration is emitted only after those tests, packet controls and
an actual retained-handle import pilot with a real successful offline probe.
The pilot uses WaitForFirstConsumer storage. The main check invokes the
repository production restore script in `check` mode with Immediate storage,
the ten source snapshots and independently captured stopped-source inventories.
It creates distinct retained content aliases and restored backend volumes,
then executes the actual ten offline production probes. Source content UIDs
and complete original specs are rechecked afterward. No source ref is patched
and no alias uses Delete.

Only the kubeconfig's authorized maintenance principal is used. This lab does
not establish protection from a cluster administrator replacing admission,
forge provider trust, or certify a production security principal configuration.

## Collector compatibility correction

The historical collector required an API-typed `VolumeSnapshotList`. With real
kubectl v1.32.3, its normal `get -o json` produces generic `v1/List` and the
collector exited 78 after the real backup snapshots were ready.
`kubectl-lab.py` uses real `kubectl get --raw` for only those two canonical
namespace list calls, preserving the genuine API server response bytes. It
does not fabricate objects, logs or readiness, or merely rename the list kind.
Raw responses are retained in `raw-api-lists/`.

For this interrupted run, `recover-collector` revalidates the stopped source
PVCs and retained live snapshot bindings, then invokes the same collector on
the already existing snapshots. `backup/collector-recovered.json` explicitly
records that the initial backup invocation failed and no new snapshots were
created. The coordinator then fixed the stock collector to accept the exact
generic `v1/List` envelope while strictly validating each item, namespace,
identity, readiness and complete ten-volume scope. The actual stock CLI passed
without the adapter and produced byte-identical output at
`backup/request-stock-collector.json`. This proves collection in this lab, not
restoration, provider signatures or release authority. Historical raw responses
and failures remain retained; a shim pass is never substituted.

## Capacity, resumption and retention

Docker's root is on a separate 40 GiB loop filesystem, so free workspace space
does not imply free CSI or image storage. The first PostgreSQL population hit
ENOSPC. Its failed Pod/log were retained as evidence, then only that owned
fixture Pod was removed and one empty-data retry succeeded. Completed source
fixture Pods are removed after recording UID/spec/logs because the backup
contract requires no source Pods. No source PVC, retained snapshot or restored
PVC is automatically removed.

Two redundant 360,617,984-byte image-import tar copies were created in the
exact node. Both matched the retained external archive before removal. The
first copy was hidden below Kind's `/tmp` tmpfs; a private mount namespace
exposed it without altering the live node's mounts. Exact paths/hashes and the
retained external archive are recorded in `released-import-staging.json` and
`released-hidden-import-staging.json`. No other images, containers, volumes,
Docker caches or host filesystems were cleaned up or resized.

The ten source volumes plus retained snapshot artifacts measured about
43.6 MiB before restore. Plan roughly 100 MiB more for physical restore data
and Pod overhead, with at least 256 MiB of available working margin. Requested
128 MiB PVC capacity is not a measurement of this hostpath driver's physical
data consumption. Stop large pulls/builds when capacity is constrained; do not
prune Docker or resize the loop filesystem under this authorization.

Use the same private output directory to resume phases; successful fixture,
packet and denial evidence is reused, not rerun. An uncertain install, partial
backup or partial production restore is refused rather than blindly repeated.
Diagnose and explicitly recover the exact interrupted phase. Historical
`blocker-*.json` files remain as failure history; they are not silently erased.
